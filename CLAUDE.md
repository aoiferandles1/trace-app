# Trace app: notes for agents

Trace is a health record a patient owns and shares with a doctor only when they say so. Designed by Aoife Randles; this repo is the working MVP. `PLAN.md` is the build plan (section 0 overrides the rest). Read it before starting a phase.

The app is being redesigned. `docs/redesign/SUPERVISOR-NOTES.md` (read first; it wins over the brief where they disagree), `docs/redesign/BRIEF.md` (the spec) and `docs/redesign/canvas/*.dc.html` (the approved boards, every value inline) govern the look. Phase 1 (tokens, fonts, icons, base components, /kit) is done; later phases rebuild each screen against its board, using only what is described under "Design system" below. Also read `AGENTS.md`: this is Next.js 16, which differs from older versions (Middleware is now `src/proxy.ts`, Cache Components is on). The docs for the installed version are in `node_modules/next/dist/docs/`.

## Run it

```bash
npm install
npm run dev         # http://localhost:3000
npm run build       # production build (/kit is a 404 there)
npm run lint
npm run typecheck   # next typegen + tsc
npm run test:e2e    # Playwright + axe against the local stand-in for Supabase; builds into .next-e2e, serves :3100
npm run test:db     # every supabase/tests/*.sql against local Postgres 17 (PGlite), each check listed
npm run test:e2e:live  # tests/e2e/live-smoke.spec.ts against the real project (.env.local); before a deploy only
```

`.env.local` (git-ignored) holds the six variables listed in `.env.example`. Never print, log or commit their values. There is no Supabase secret key anywhere in this project. Only `npm run dev` and `test:e2e:live` use it.

### Tests run against a local stand-in for Supabase

`tests/support/local-supabase/` (README there): PGlite runs `bootstrap.sql` (the roles, `auth` schema, `extensions.pgcrypto` and publication Supabase provides) and then every migration unchanged, and `server.ts` (port 54329) answers the app's Auth, PostgREST and Realtime calls, with RLS applied per request as PostgREST does. `playwright.config.ts` starts it, then `next build` + `next start` with `TRACE_E2E=1` (the build goes in `.next-e2e`, `/kit` renders there) and the values in `tests/support/local-env.ts` (a local portal server secret, so the portal API works; `__NEXT_PROCESSED_ENV` stops Next.js reading `.env.local`). `E2E_SKIP_BUILD=1` reuses the last e2e build when only tests changed; outside CI a running stand-in and app are reused (restart them after a migration or an app change). A new table or function needs nothing (it is in the migrations); a new query shape goes in `rest.ts`, something Supabase provides that a migration needs goes in `bootstrap.sql`. Never edit an applied migration for the stand-in. `tests/e2e/helpers/sql.ts` runs SQL as the owner (moving a share's expiry, for Time's up).

In this container Chromium is preinstalled at `/opt/pw-browsers/chromium` and `playwright.config.ts` uses it. Do not run `playwright install`. `@playwright/test` and `playwright-core` are pinned to 1.63.0 (an `overrides` entry keeps `@axe-core/playwright` on the same version); keep them together.

## Where screens go

- Patient screens: `src/app/(patient)/<route>/page.tsx` (route group, so URLs stay `/home`, `/record`...). Wrap each in `PatientShell`.
- Portal screens: `src/app/view/...`: the steps outside a session in `PortalShell`, the live record in `RecordFrame` (see "Doctor's portal").
- A component used by one screen only lives next to it in `_components/`. Move it to `src/components/` once a second screen needs it.
- The routes are in PLAN.md section 6; the redesign's boards are in `docs/redesign/canvas/` (titles in `canvas.json`). Every new screen and every new string goes in `docs/REVIEW.md`.

## Patient app (Phases 3 to 6, 8 and 9)

- Signed-in routes live in `src/app/(patient)/`; sign-up steps 3 to 7 in `src/app/signup/(account)/`. Both layouts wrap `PatientSessionGate` (`src/components/patient/PatientSession.tsx`) in `<Suspense>`. The gate checks the session in the browser and redirects (signed out to `/`, unfinished sign-up to its step by `profiles.onboarding_step`). Every page there exports a wrapper that renders its screen inside `<SessionReady>`, and reads the user with `usePatientSession()` (`userId`, `email`, `profile`, `setProfile`, `reloadProfile`).
- Screens frame themselves with `TabScreen` (the five tabs) or `SubScreen` (details and forms) from `(patient)/_components/Screens.tsx`. `SubScreen` takes `titleSize="md"` (24/30, FamilyA2 and InsuranceA2), `action` (the header's right slot: the pencil that opens an edit form), and `tabBar` for detail screens (the boards draw the tab bar on Medication, Timeline, Family and Insurance); forms and focused flows (upload) never get it. A detail screen's caption under the title is the body's first line, `-mt-1.5 text-body text-ink-2`, in a `pt-3.5` column (MedDetailA2's spacing). Both render `DemoMarker` (the "Demo with sample data" strip, demo accounts only) and `LiveBannerSlot`, the seam for the live share banner. `TabScreen banner={null}` hides the strip (Home shows a live share in its `TodayCard` instead). `PageHeader` is 56px; `height={48}` for RecordA2, `variant="greeting"` for Home (one h1, "Good afternoon, Jane"). `LoadStatus` is the loading state (quiet grey blocks, "Loading" for screen readers) and the load-failed `StateMessage`.
- Data: the browser Supabase client, loaded with `useLoad()` (`src/lib/useLoad.ts`). Redesigned screens read the record through `my_record(section)` with `loadSection()` / `loadSections()` from `src/lib/patient/record.ts`, which also types every shape (entries, medications and periods, events, relatives, documents, insurance) and holds the words and dates for them: `ENTRY_KIND_LABEL`, `entryIcon()`, `entryTitle()`, `conditionCaption()`, `capitalise()`, `formatAtPrecision()` / `formatRange()` (a period or event at its day, month or year precision), `medicationCaption()` and `medicationNowLine()` (MedsA2, MedDetailA2), `eventCaption()` / `eventMeta()` (TimelineA2), `documentCaption()`, `formatBytes()`, `parseStrength()`, `RELATION_OPTIONS`, `CONDITION_CATEGORIES`, `UNIT_OPTIONS`, `MAX_DOCUMENT_BYTES`, `URGENT_REFILL_DAYS` (5: a refill is urgent at 5 days or fewer, owner's decision; Home and Medications both use it) and `errorCode()` (the database's code from an error). Never call the functions supabase/README.md marks [old app] (`seed_demo_record`, the old `create_share_code`, `export_my_data()` without `version`). Dates and "today" are Irish time: use `src/lib/dates.ts`.
- Next.js keeps earlier screens in the page, hidden. Element ids must be unique per screen instance (forms use `useId()`), and tests should prefer `getByRole` (it skips hidden elements) or add `.filter({ visible: true })`. A screen can come back from memory with its state, so every add and edit form goes through `useFormScreen()` (`_components/forms/FormBits.tsx`): it gives `formId`, `busy`, `formKey` and `control` (`formId`, `onSaving`, `onSaved`); the form calls `onSaved(href)` after a successful save, which announces "Saved.", leaves with `router.replace` and, as the screen hides, clears the busy flag and bumps `formKey`. Key the form on `formKey` (plus the saved row's `updated_at`, or its JSON for a `my_record` shape, on an edit form). A row seeded from saved data is keyed on those values, and data is re-read with `useLoad`'s `reload()` (which shows loading again after a failure) rather than copied into local state. Save errors use `saveFailedMessage(error)`.
- A screen that can be opened from more than one place reads its Back from `?back=` (`src/lib/back.ts`: `withBack(href, back)`, `useBack(fallback)`, `useHere()`): the Add sheet's rows pass the screen under the sheet, /add passes /add, Home and the share summary pass themselves to an entry, the sign-up and privacy screens to Terms. Only paths inside the app are accepted.
- Delete lives at the bottom of each Edit form (entries, conditions, medications, events, relatives, care team, documents, vitals); the one exception is a doctor's notes entry, which has no form. The confirm in a delete sheet is `Button variant="danger"`.
- Every patient and sign-up tab gets its title from its address (`RouteTitle` in `src/lib/patient/pageTitle.ts`, rendered by both layouts), never from the record. Add a route there with a new screen.
- The gate reads the cookie session locally, then runs `getClaims()` (local signature check), the profile read and `my_share_session()` in parallel. In the record area it wraps everything in `ShareSessionProvider` (`src/components/patient/ShareSession.tsx`): `useShareSession()` gives `session` (live, else the latest), `loaded`, `refresh()`, `setSession()` and `announce()`. It subscribes to Realtime on the user's `share_sessions`, polls `my_share_session()` every 3 s while anything is live, renders the access request sheet (`AccessRequestSheet`) over any screen when the status is `requested`, and owns the one polite live region for timer milestones. It also keeps `notice` (with `dismissNotice()`): one visible line for an outcome seen happen live (a share ended, a request denied or timed out), which `LiveBannerSlot` draws at the top of every signed-in screen (`ShareNoticeStrip`) until it is dismissed or a new share starts; Home's `?ended=` line hides itself when the notice already says it. The live strip says "access ends soon" in the last 5 minutes. Pages never decide a share has expired; at zero they call `refresh()`.
- Share helpers (types, words, durations) are in `src/lib/patient/share.ts`. `SCOPES` is the one list of share sections (ten: label, icon, switch key; Safety info and Medications have no key: always shared), in the order every screen shows them. Insurance is not a scope: it is personal (owner's decision), so `createCodeArgs()` always sends `share_insurance: false` and no screen lists it. `GP_VISIT_DEFAULTS` has Conditions, Recent visits, Full timeline, Care team and Medication notes on (owner's decision); `sharedScopes()` / `notSharedScopes()` turn a session's switches into "Sharing" and "Not shared", and `createCodeArgs()` builds the new `create_share_code` call with every switch named, insurance off (naming them is what reaches the new version). `rememberedPrefs()` / `rememberPrefs()` keep the last share's choices in this browser (Mental health always starts off). Never hard-code a list of what is shared. The patient's words for it: share, sharing, access (never "session"); a doctor's notes entry is "Doctor's notes" and `entryTitle()` titles it "Notes from Dr X". The code screen's rows (with counts) come from `src/lib/patient/useShareSummary.ts` and draw with `src/components/patient/SharedSummaryCard.tsx`. Routes: `/share` (`?appointment=<visit id>` from Home's today card; while a doctor has access it opens `/session`), `/share/code`, `/session` (active and Time's up; "End sharing now" is the shell's pinned footer and asks once), `/session/ended?id=` (the summary), `/access-log` (shown as "Share history"). When a share ends, `/session` sends the patient to `/home?ended=<id>`, where one line links to the summary.
- Countdowns use `useNow()` (`src/lib/useNow.ts`), which runs on the database's clock: the browser Supabase client measures the offset from every response's `Date` header (`src/lib/serverClock.ts`). Do not count down from `Date.now()` directly.
- Sign out and account deletion call `leaveForWelcome()` (a full page load), so screens Next.js keeps hidden in memory do not keep the previous person's record. A `BottomSheet` closes itself when its screen is hidden; close confirm sheets in state after their action succeeds, or they reopen on Back.
- Ending a session writes the row twice in one transaction with the same `updated_at`; `pick()` in `ShareSession.tsx` keeps the version with `notes_entry_id` on a tie. Do not resolve ties by arrival order.
- The centre plus opens the Add sheet (`src/components/patient/AddSheet.tsx`: `ADD_ROWS`, `AddRows`, `AddSheet`), plain rows to each form: Add a visit (`/add/appointment`), Add a medication, Add a condition, Add a relative, Upload a document, Log a note (`/add/note`), Add to your timeline, Log vitals (`/add/vitals`). `/add` shows the same rows as a screen (the rail's Add). `AddRows` takes `back` (the sheet passes the screen under it). Add a row there when the app can add something new. Long forms put their less used fields under `MoreDetails` (FormBits).
- Pages that are only a state (not found, an error, the record not loading) use `StatePage` (`src/components/layout/StatePage.tsx`): the wordmark, a centred title, one line, one text button. `src/app/not-found.tsx` and `src/app/error.tsx` are the app-wide ones; inside a screen use `LoadStatus` / `StateMessage`.
- Profile is a list (`/profile`); its rows open `/profile/details` (with `/profile/email`, Change email), `/profile/insurance`, `/profile/documents`, `/profile/care-team`, `/access-log`, `/profile/privacy` ("Privacy and data": terms, export, `/record/print` to print, delete account) and the case study. Record's tabs are in the address (`/record?tab=conditions|family`); detail screens send the patient back to their tab. Record links to `/record/timeline`, `/record/family` (`?relative=<id>` for a relative's row, `?add=relative` for "Add a relative") and `/record/[id]`; Home's refill tiles to `/meds/[id]`. Record's upcoming rows are not links (brief 4.3).
- Phases 4 to 6 routes: `/meds` (`?tab=past`), `/meds/[id]` (`?from=past`), `/meds/[id]/edit`, `/meds/[id]/change` (`log_strength_change`; a strength is never edited any other way, so the edit form hides it once a medication has periods), `/meds/[id]/notes/[periodId]` (a period's note and `note_shared`; a new note starts shared, owner's decision), `/record/timeline` (`?event=<id>` opens its sheet), `/record/timeline/new`, `/record/timeline/[id]/edit`, `/record/family`, `/record/family/new`, `/record/family/[id]/edit`, `/profile/insurance`, `/profile/insurance/manual` (`?other=1`; `?edit=1` edits a hand-typed policy), `/profile/documents`, `/profile/documents/[id]`, `/profile/documents/[id]/edit` (name, date, Delete), `/profile/documents/upload` (a photo over 3 MB is scaled down in the browser first). Review additions: `/record/vitals`, `/add/vitals`, `/record/vitals/[id]/edit` (`VitalsForm`), `/record/search` (Record's header magnifier), `/record/print`. Upcoming visits and refills offer an .ics file (`src/lib/patient/calendar.ts`). The family tree's positions come from `record/family/_components/treeLayout.ts` (FamilyA2's coordinates as anchors). Insurance's provider sign-in is the mock in `src/lib/patient/insuranceMock.ts` (marked as a stand-in; no password anywhere). Documents are opened through `GET /api/documents/<id>`, which serves the stored type with `nosniff`, `Cache-Control: no-store` and a sandbox CSP that `next.config.ts` sets for that path (config headers replace a route's own); a PDF downloads, a photo opens in its own tab, never inside a page.
- Demo accounts (`isAnonymous`) get `DemoMarker` (a `DemoStrip`) at the top of every screen, with "Open the doctor's side" when not inside /demo's frames, and "Reset demo" in Profile (signing out of a demo asks first). "Try the demo" and "Reset demo" call `seed_demo_record_v2()`. Real accounts never see the strip. `/demo` (outside the gate) frames `/` and `/view?demo=1`; `next.config.ts` sends `frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN` on every route. The daily cleanup is `GET /api/cron/cleanup` (Bearer `CRON_SECRET`, scheduled in `vercel.json`); never call it with the real secret from tests.

## Doctor's portal (Phase 7)

- `/view` (`_components/ViewFlow.tsx`) is every step before the record: loading, the name step (remembered in this browser under `trace.portal.clinician`), the code (the fourth digit submits; wrong, expired and locked are the code step's own error line, not screens), waiting (session indigo, polls `portal_status` every 2 s, says so when polls fail), declined, timed out, withdrawn. Approval goes straight to `/view/session`. Browser Back steps back (code to name, waiting to code, which cancels the request) through `history.pushState` entries carrying `traceStep`. The demo (`?demo=1`, remembered for the tab in sessionStorage `trace.portal.demo` by `useDemo()`/`readDemo()` in `_lib/hooks.ts`) starts at the code as Dr Hennessy, keeps its edited doctor in state only (never `saveClinician`), and keeps `?demo=1` (`portalHome(demo)`) and the demo footer through the session. The first status call goes through `firstStatus()` (`_lib/api.ts`), which shares an in-flight call so a double mount never mints two portal tokens. The steps use `PortalShell` + `PortalSplit` (the boards' 520px step and 340px side list, `StepRows`/`StepRow`), `PortalHeader` and `PortalFooter` (`demo` swaps the right-hand note). `/view/about` is "About the portal" (For your practice, Privacy and security). Any other `/view/...` address is the portal's own not-found page (`view/[...missing]` calls `notFound()`, `view/not-found.tsx`).
- One session per frame: Next keeps `/view/session`'s layout alive, hidden, with its state, while the doctor is on `/view`. `SessionScope` (`session/_components/SessionFrame.tsx`, used by the layout) remounts `SessionFrame` with a new key when the layout is hidden (a `useLayoutEffect` cleanup) and when a status's `approved_at` differs from the one the frame started with, so notes, overview, scope, clock offset, selected rows and loaded sections never reach the next session (`tests/e2e/portal-session-reset.spec.ts`). `ViewFlow` starts afresh the same way. Before a remount on hide the frame sends unsaved notes to the session they belong to; never after it has met a different session. Mocks must keep `approved_at` stable within one session (`statusOf()` does).
- `/view/session/*`: `SessionFrame` polls every 5 s (two failures in a row show "Trace can't be reached"), loads the overview once for the header (`useSession().overview`; a failure shows Try again and keeps End session), and renders `RecordFrame`: `PortalSidebar` (the rail, built from `VIEWS` in `src/app/view/_lib/sections.ts` and the scope), `PatientSummaryCard` (h1 is the patient's name; facts row; the 3px `Countdown`), the view, then `ResizableNotes` around `SessionNotesPanel` (only when the patient allowed notes; otherwise the header gets a "Session notes: Not allowed" fact and there is no column). Views are in `session/_components/Views.tsx`, one route each (`visits?id=`, `medications?id=`, `timeline?id=`, `care-team`, `family`, `documents`, `mental-health`, plus `end`), and load their own section with `useSection(name)` (which returns `retry` for the failed state). A view selects by writing `?id=` with `window.history.replaceState` (no navigation; Next keeps `useSearchParams` in step), so other views link straight to an item; `TwoPane`'s `picked` brings the detail into view when the panes are stacked.
- Notes: the frame owns the draft and autosaves after 1.2 s; `saveNotes(manual)` spins the button and announces only for a pressed Save; the status ("Saved 11:29") sits beside the heading. Fields have `maxLength` 5,000 (the database's limit) and grow with `field-sizing-content`. The panel is mounted in a different shell when the countdown ends or access pauses or resumes, so `createFocusMemory()` carries the focused field and caret to the new panel, and the paused screen does not take focus from a field. `endSession()` will not end while the latest notes fail to save unless called with `withoutLatestNotes` (`endProblem` "notes"; a failed end is "failed"); both show where End session was pressed (`EndProblemNotice`). The ended screen shows the notes it held with Copy and Print. Only a number (the notes width, `trace.portal.notesWidth`) goes into storage.
- Insurance is personal (Aoife, Nov 2026): it is not in `VIEWS`, has no route, and `SECTIONS` leaves it out, so `/api/portal/record?section=insurance` is `invalid_section` whatever the scope says.
- Not shared means not fetched: the frame checks the view's scope before it mounts it (an ungranted address shows `NotSharedView` and asks for nothing); `/api/portal/record` calls `portal_get_record` with `version: 2` and answers an ungranted section with 403 `not_shared`. To add a view: add it to `VIEWS` (with its scope key), a page under `session/`, and its section to `SECTIONS` in `src/app/api/portal/_lib/portal.ts`.
- Documents open through `/api/portal/document?id=` (the file itself, with its stored type, `nosniff`, a `sandbox` CSP, `no-store`; a PDF as an attachment, a photo inline); `next.config.ts` repeats the CSP for that path, since the site-wide header would replace it. Anything it will not serve is a 404 with one short HTML page, the same whatever the reason.
- When access is not active (paused, ended, or the countdown reaching zero, which hides the record at once and asks the database), the frame stops rendering the views, so their data leaves memory; nothing about the patient goes into browser storage. The frame keeps the document titled so Next's route announcer never stores the patient's name (the h1).
- Next keeps earlier views alive and hidden: in tests use `getByRole` or `.filter({ visible: true })`, and state in a view must follow a changed `?id=` (Medications does).
- Screenshots: `patient-screens` (opt-in `E2E_SCREENS=1`, phone project, one demo sign-in, the sharing screens through the real loop) writes the 390 x 844 phone screens to `docs/redesign/screens/after/`; `docs/redesign/screens/before/` holds the old design from the live site.
- Tests: `portal-loop` (the real loop), `portal-scopes` (each scope alone, the API refusals, medication notes, documents, mental health), `portal-states` (stand-in responses from `tests/helpers/portal-mocks.ts`: made-up data, time-based states, the notes panel), `portal-session-reset` (two sessions in one page), `portal-review-fixes` (the review's portal fixes, stand-in data), `portal-screens` (opt-in `E2E_SCREENS=1`, writes `docs/redesign/screens/after/`). They drive the patient with `tests/helpers/portal-patient.ts` (import its `test`: the `patient` fixture is a fresh seeded patient per test, through the local stand-in, so the real loop, `portal-scopes` and the database-backed `portal-states` tests run locally with the local server secret; `seed_demo_record_v2`, the new `create_share_code` with all four new scopes named, and the patient app's defaults: Full timeline and Medication notes on, Insurance off).

## Shells

```tsx
<PatientShell
  demo={<DemoMarker />}           // "Demo with sample data", demo accounts only, very top
  banner={<LiveBannerSlot />}     // the live share strip while a doctor has access
  header={<PageHeader title="Record" />}
  tabBar={<TabBar />}             // only on the five main screens
  footer={<Button fullWidth size="lg">Continue</Button>}  // pinned bottom action (sign-up, forms)
>
  ...screen content (inside <main id="main">; add the 20px gutter, px-5)...
</PatientShell>
```

Full width up to 480px, a centred 430px column above. No fake iOS status bar. The frame is one screen tall, as on the boards: the demo strip, banner, footer and tab bar stay put and only `<main>` (with the header inside it) scrolls, so nothing sits under the tab bar. Do not add `sticky` bars inside a screen; use the shell's slots. `tone="session"` for the sharing screens (share code, session active, Time's up): session indigo, white text, white focus rings. Add `<ThemeColor tone="session" />` on those screens so the browser chrome matches (the access request sheet sets it while open). ### Home screen

## Supabase

- Client Components: `import { createClient } from "@/lib/supabase/client"`. Runs as the signed-in user under RLS.

- Cache Components is on: anything that reads cookies (the server client does) must render inside `<Suspense>`, and must not be awaited at the top of a layout. See `node_modules/next/dist/docs/01-app/02-guides/authentication-with-cache-components.md`.

- `src/proxy.ts` only refreshes sessions; it redirects nobody. Protect pages in the pages/layouts. It skips `/kit`, `/view` and `/api/portal`.
- When the generated database types land, pass them as the client generic (`createBrowserClient<Database>`).

## Design system (BRIEF.md sections 1 to 3)

Calm, indigo, not text heavy. The owner rejected these, so never add them: shadows (cards are a 1px hairline), icons in tinted circles or squares, dot + "Live" stamps, pulsing dots, status pills for decoration, a banner across the portal, gradients, glassmorphism, emoji, illustrations, On/Off words on toggles, decorative dividers between inline facts, repeated explanations. ### Conventions

- Interaction states: use the `hovered:` and `pressed:` variants (globals.css), not `hover:`/`active:`. They also respond to `data-force="hover"` / `"press"` / `"focus"`, which is how /kit pins states.
- Focus: a global 2px ink `:focus-visible` outline with a 2px gap. On session indigo add `on-session` (shells and the rail do) so the ring is white. Never remove outlines. In a container that clips, inset the ring (`focus-visible:-outline-offset-2`).
- Touch: 44 x 44 on the phone (`hit-area` and `hit-area-square` utilities keep a small control's look), 32px for desktop pointer UI.
- `cn()` in `@/lib/cn` only joins classes; it does not merge. Pass `className` for layout (margin, width, grid), not to restyle a component. If a component needs a new look, add a prop.
- Copy: short, plain, no em dashes. Use the boards' words for the screens they show, and corrected values from PLAN.md section 11, never the old Figma mistakes.

## Accessibility (PLAN.md section 10, WCAG 2.2 AA)

- Every field has a visible label (`label` prop). Errors are words, passed as `error`; they are tied to the field with `aria-describedby`.
- Status is never colour alone: flags say "low" or "high", urgent captions say what is due, locked items say "Not shared" or "Always shared", the safety strip says "allergy".
- Timers: never put a ticking countdown in a live region. The patient side announces session start, 5 minutes left, 1 minute left and ended in ShareSession's polite region; `Countdown announce` gives a component its own (5 min, 1 min, 10 s) where nothing else announces. `formatCountdownSpoken` helps.
- `BottomSheet` is a modal `<dialog>`; focus moves in, Tab wraps inside, and focus returns to the opener on close.
- Every new screen gets a Playwright test that runs `expectNoAxeViolations(page)`, and an entry in `tests/e2e/a11y.spec.ts` (320px reflow, a Tab round checking every stop is visible with an unclipped focus ring). A new patient screen with the rail also goes in its desktop test (1024, 1280 and 1440: the rail, the column or panes, axe and the Tab round). In a container that clips (`overflow-hidden`, a scrolling row), give the ring room or inset it (`focus-visible:-outline-offset-2`). The /kit test is in `tests/e2e/kit.spec.ts`.
- Contrast: every text pairing in the token table passes 4.5:1 and every icon or control edge 3:1, except the segmented control's container (`border-control`, 1.3:1, as the boards draw it; its choice is the accent fill). Text fields and code boxes use `border-field` (3.2:1), never `border-control`. The kit's Tokens section computes them live. If a new pairing fails, darken the token slightly, never lighten, and record it in `docs/REVIEW.md` with every other substitution.
